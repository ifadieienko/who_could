# Версия мастерской: обновление и настройки

## Схема и перенос данных

`0009_workshop_platform` создаёт отдельную модель мастерских, сотрудников, клиентов, устройств и ремонтов. Она не удаляет прежние таблицы. Старые пользователи, формы, заказы и склад переносятся в **одну** «Перенесённую мастерскую»: в прежней модели не было идентификатора организации, поэтому безопасно восстановить несколько организаций автоматически невозможно. До запуска владельцу следует проверить состав сотрудников. Если прежний экземпляр обслуживал независимые компании, сначала подготовьте явную таблицу соответствия и отдельную миграцию — общий автоматический перенос для такого случая не подходит.

Прежние admin становятся владельцами; если admin отсутствует, владелец — пользователь с минимальным ID. Прежние master получают роль мастера, остальные — приёмщика. Пароли сохраняются; всем потребуется войти заново. Новый API не предоставляет глобального администратора или удаления пользователей с каскадным удалением заказов.

Приёмки сохраняют значения, исходную форму и личные этапы старой доски; выданные заказы остаются выданными. `external_id=legacy:<старый ID>` позволяет сопоставить записи. Произвольные старые поля не разбираются эвристически на ФИО/модель/серийный номер: они доступны в карточке, а новые заказы используют отдельные записи клиента и устройства. Старые формы могут потребовать новой версии с ключами, ожидаемыми выбранным процессом. Нельзя привязать несовместимую форму к новому процессу.

При первом запуске API старые `data:image/...` преобразуются в защищённые JPEG и миниатюры в `UPLOAD_DIR`. Процесс повторяемый; исходные старые таблицы сохраняются. Если старое изображение повреждено, его исходное значение остаётся в базе и появляется событие `legacy.photo_failed`; остальные заказы продолжают работать. Оператору следует проверить такие события перед удалением какого-либо архива. При большом архиве фотографий выполните `python -m app.legacy_photos` в контейнере после миграций, до запуска сервиса, и увеличьте окно обслуживания/healthcheck при необходимости.

## Порядок выпуска

1. Проверьте CI на MariaDB, включая заполненную миграцию и конкурентное согласование, и браузерные тесты.
2. Сделайте SQL-копию и архив `UPLOAD_DIR`; испытайте восстановление в отдельной среде.
3. На копии рабочей базы выполните `alembic upgrade head`, `python -m app.legacy_photos`, `alembic check`. Сверьте число старых/новых заказов, формы, выданные устройства, сотрудников и фото. Проверьте вход прежним аккаунтом.
4. После проверки выполните обновление штатным `server.sh update` в согласованное окно. Не запускайте одновременно старые и новые API на общей базе.
5. Пройдите приёмку, клиентское согласование, ремонт, выдачу и гарантийный возврат; распечатайте QR на вашем принтере.

Обратный Alembic downgrade намеренно запрещён: он уничтожил бы историю новых ремонтов. Откат — предыдущий образ плюс соответствующая SQL-копия и фотографии. Успешные изменения после копии при таком откате потеряются; это нужно учитывать при планировании окна.

## Настройки приложения

Локально — `backend/.env`. На сервере используйте отдельный `/opt/who-could/config/workshop.env` (права `0600`, вне Git), подключаемый Compose дополнительно к deployment.env. Путь переопределяется `APP_SETTINGS_ENV`; требуется Docker Compose >= 2.24. Этот файл не перезаписывается `server.sh configure`. После изменения настроек пересоздайте backend через configure либо Compose с действующими deployment overlays. Секреты не вставлять в репозиторий.

| Переменная | Назначение |
|---|---|
| `PUBLIC_URL` | Абсолютный HTTPS-адрес frontend без `/api`, например `https://repair.example.com`; QR, ссылки в письмах, возврат из Stripe |
| `UPLOAD_DIR` | Локально `./uploads`; Docker фиксирует `/app/uploads` и постоянный volume |
| `BILLING_ENFORCED` | По умолчанию `false`; включить `true` после настройки и проверки платежей |
| `STRIPE_SECRET_KEY` | Сначала test-mode ключ Stripe |
| `STRIPE_PRICE_ID` | Один recurring Price: подписка на мастерскую, а не на пользователя |
| `STRIPE_WEBHOOK_SECRET` | Секрет endpoint `/api/billing/webhook` |
| `SMTP_HOST`, `SMTP_PORT` | SMTP-сервер и порт, по умолчанию 587 |
| `SMTP_FROM` | Отправитель; обязателен для worker и сброса пароля |
| `SMTP_USER`, `SMTP_PASSWORD` | Авторизация, если требуется |
| `SMTP_STARTTLS` | По умолчанию `true`; отключать только для контролируемой локальной инфраструктуры |
| `SMTP_MESSAGE_DOMAIN` | Домен стабильного Message-ID писем |

### Подписки

Создайте recurring Price и настройте Customer Portal в Stripe. Webhook должен передавать `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`, `invoice.payment_failed`. Интеграция запрашивает API версии `2024-06-20`; endpoint Stripe следует настроить на эту же версию. Сервер проверяет подпись исходного тела, свежесть timestamp, ID события и запрашивает актуальную подписку у Stripe; клиент не может прислать собственную цену/права доступа.

Новая мастерская получает 14 дней trial. Проверка записи допускает ещё 7 дней grace после trial/последнего оплаченного периода; затем доступны чтение и экспорт. При `BILLING_ENFORCED=false` записи не блокируются. Stripe Checkout оплачивает подписку на сервис; оплаты ремонта вводятся отдельно как учёт уже полученных денег.

Перед `BILLING_ENFORCED=true` проверьте test-mode Checkout, повторный и переставленный webhook, неуспешное продление, отмену, Portal и восстановление доступа. Обработка webhook покрыта mock-тестами, реальные платежи в рамках этой разработки не выполнялись. Тарифы с лимитами пользователей, годовые скидки, налоги и инвойсинг мастерской не реализованы.

### Уведомления

В очередь попадают ссылка согласования сметы (при настроенном PUBLIC_URL), готовность заказа и сброс пароля. Запускайте из cron раз в минуту:

```cron
* * * * * /opt/who-could/current/server.sh mail >> /var/log/who-could-mail.log 2>&1
```

Штатная блокировка server.sh и выполнение worker внутри действующего backend предотвращают работу отдельного старого worker во время обновления. Можно запускать `python -m app.mail_worker --once` вручную; непрерывный режим предназначен для самостоятельной оркестрации. До 5 попыток с задержкой, ошибки/статусы видны владельцу в разделе подписки. Уникальный ключ очереди предотвращает повторное создание одного события. SMTP имеет семантику как минимум однократной доставки: при сбое между отправкой и commit возможен дубль; стабильный Message-ID помогает получателю его обнаружить. SMS/WhatsApp не подключены.

## Границы этой версии

- Конструктор использует сетку 1–3 колонок, номер строки 1–100 и перестановку кнопками. Нет drag-and-drop, вложенных повторяемых секций или произвольных формул. Форма одна на заказ с разделами для приёма и ремонта; правила обязательности можно задавать по этапам.
- Версии процессов и форм замораживаются в заказе; массового перевода уже открытых заказов на другую схему нет.
- Сотрудников создаёт владелец с отдельным рабочим email/начальным паролем. Присоединение существующего аккаунта по приглашению и подтверждение email регистрации не реализованы. Пароль можно заменить через восстановление при настроенном SMTP.
- Согласование по секретной ссылке фиксирует решение, имя и время; это не квалифицированная электронная подпись. Утечка ссылки даёт возможность принять решение до истечения срока. Истекающие токены хранятся в базе хешами; тело ожидающего email содержит ссылку.
- Склад — сохранённые пользовательские таблицы. Нет количественного движения запчастей, резервирования, закупок, себестоимости или интеграции с оплатами.
- Экспорт включает историю, сотрудников, файлы и данные мастерской; не включает пароли, сессии, токены и настройки провайдеров. CSV-импорт не восстанавливает ZIP-снимок: аварийное восстановление делается SQL + архивом фотографий.
- Нет офлайн-синхронизации, OCR, фискального регистратора, нескольких валют ремонта, автоматических возвратов платежей или мониторинга инфраструктуры.

Эти ограничения отделены от исправленных дефектов; версия не заявляется как полностью завершённый коммерческий SaaS без эксплуатационной приёмки.
